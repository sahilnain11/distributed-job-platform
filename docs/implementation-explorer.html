Understand the system · 01

One job. Several decisions.
One source of truth.

Job

The accepted intention

Stable ID across attempts and manual cycles. Example: “run this simulation.”

Attempt

One execution owner

New UUID and lease for every committed claim. Failed or expired history is never reset.

Delivery

A notification, not a command

Can be duplicated or arrive late. PostgreSQL still decides whether a new claim is allowed.

Why these pieces?

PostgreSQL: transactions, row locks and durable shared facts.

RabbitMQ: buffered delivery and bounded consumer intake.

Outbox: save the intent to publish without needing an atomic DB/broker commit.

Attempt tokens: prevent stale workers from changing platform state.

Logical roles ≠ separate microservices

The same Spring Boot JAR can run API, publisher, workers and pollers together—or split into configured processes.

Our local scaling tests used one API/publisher process plus worker processes. They still share one database and broker; this is not multi-host HA.

    Design choices and failure windows · 03
    Safety comes from boundaries.
    A transaction, a row lock, a request key, a lease and an ACK solve different problems. None replaces all the others.
    
  
    1. Atomic acceptance
    Job + payload + unpublished outbox + saved HTTP response commit together. A later failure rolls back already-flushed inserts too.
    Without this: the client may receive an accepted job that has no durable notification path.
    2. Unique request reservation
    INSERT ... ON CONFLICT (client_id, operation_scope, idempotency_key)
DO NOTHING;

Inserted? Perform operation and save response.
Conflict? Read committed winner, compare full input hash.
    A competing insert waits for the first transaction. This works across processes; a Java in-memory lock would not.
    3. Lock → recheck → write → commit
    SELECT ... FROM jobs WHERE job_id = ? FOR UPDATE;

Authorize using current state + attempt token + fresh DB time.
Write all related outcome records in this transaction.
Do not hold the transaction during handler work.
    Transactions keep related writes atomic. Row locks serialize competing decisions. Fresh time rejects a lease that expired while waiting.
    
  
    Request idempotency
    Same scoped key + equivalent input → same saved response. Different key → different operation. Replay is not a current-state read.
    Delivery deduplication
    Repeated notifications consult current DB state. Only a QUEUED job can be claimed; no message-ID memory cache is needed for authority.
    Business idempotency
    An external payment/email needs its own stable business identity. Our attempt token cannot undo or fence arbitrary remote effects.
    
  
    Why not one DB + Rabbit transaction?
    A SQL transaction around a network send does not make the broker part of PostgreSQL's commit. We deliberately keep the outbox and accept duplicates.
    Confirm + routing check precede the publication mark. If the mark fails, resending is safer than silently losing the notification.
    ACK does not mean success
    A committed retry schedule or terminal failure can justify ACK. So can a confirmed duplicate/stale delivery. Unknown commit state cannot.
    Malformed and confirmed missing-job references are rejected without requeue. V1 has no dead-letter queue.
    
  
    Test your reasoning
    If success committed but ACK was lost, should the handler run again?
    Not merely because of redelivery. The claim sees COMPLETED and returns DUPLICATE; the notification can be ACKed without another attempt.
    Why is “SELECT first, INSERT if missing” not enough for request deduplication?
    Two processes can both see no row. The unique reservation insert is the actual concurrency guard; the later read sees the committed winner.
    Is flush the same as commit?
    No. Flush sends SQL within the transaction. A later failure can still roll all those inserts back.
    Does a unique RUNNING-attempt index prove only one Java handler exists?
    No. It limits recorded database state. An expired old process may continue physically; its token/lease prevents platform writes, not external effects.
    

    


    
  
    History, ownership and delayed work · 04
    Retry the job. Never rewrite its history.
    A job has a current state; each attempt has its own permanent identity. Automatic retries and manual cycles share the same job ID, not the same execution token.
    
  
    QUEUED→RUNNING→COMPLETED
    RUNNING→RETRYING→ due + outbox →QUEUED
    RUNNING→ permanent / exhausted →FAILED→ new manual key →QUEUED, cycle 0
    
  
    Four attempts, not four extra retries
    Failed/expired cycle attemptAction
    1Eligible after 1s
    2Eligible after 2s
    3Eligible after 4s
    4Terminal FAILED
    Polling/publication/queue delay comes after minimum eligibility. Permanent failure stops immediately. Recovery marks old attempts EXPIRED, not FAILED.
    Two counters, two meanings
    attempt_count: lifetime claims; never reset.
    cycle_attempt_count: claims in the current four-attempt budget; reset only by an accepted manual retry.
    Initial failure cycle: lifetime 1, 2, 3, 4
Manual retry accepted: lifetime 4, cycle 0
Next claim: lifetime 5, cycle 1
History remains: attempts 1–4 are not deleted.
    
  
    Replay happens before manual retry eligibility.
    Old key A returns its original 202 even after another failure. It never creates another cycle. A new intentional cycle needs new key B and current FAILED state.
    
  
    Lease: 30 seconds
    Renewal requested every 10s; control checks every 1s. An expired lease cannot be revived. Equality is expired.
    Runtime: 5 minutes
    From immutable attempt start. Heartbeat does not extend this. Completion repeats the runtime guard.
    Broker ACK timeout: 10 minutes
    From delivery. Independent of the lease/runtime. Channel closure can redeliver, not force-stop Java.
    
  
    Why check time after locking?
    Lease deadline:             12:00:30
Transaction starts:         12:00:29
Waits for another row lock…
Lock obtained / DB check:   12:00:31

Result: lease expired → old success forbidden.
    Cancellation has a cost
    Our simulation observes interrupt/cancellation flags. Other handlers may not. A canceled but alive handler still occupies its slot.
    Separate four-thread/four-connection supervision protects against primary-pool starvation—not DB failure or a paused JVM.
    

    


    
  
    Evidence and limits · 05
    Measured locally. Not promised universally.
    Latest completed verification recorded 173 Java tests and 71 Python tests passing. This page does not rerun them or check live service health.
    
  
    173
    Java tests
    Real PostgreSQL/RabbitMQ where needed, HTTP acceptance races, transactions, duplicates, leases, crashes and telemetry.
    71

    Measurement arithmetic, orchestration and cleanup; mostly mocked external actions, not 71 live deployments.
    6,000

    Signals are not the ledger
    Lifecycle metrics/logs emit after commit but may miss a post-commit process crash. They reset on restart. PostgreSQL history is authoritative.
    Database gauges read a cached snapshot. Check snapshot freshness/up; a stale count can look plausible. Scraping does not query PostgreSQL.
    Do not sum repeated global DB gauges across worker instances or treat configured capacity on a disabled API consumer as available slots.
    Proven scope vs deferred work
    Controlled intact-storage service/worker recovery, not permanent-volume-loss resilience.
    Local scaling/container packaging, not Kubernetes, multi-host HA, TLS/auth/tenant isolation or production readiness.
    Short explicit workload measurements, not 1,000/s or 99.9% availability proof.
    Creation-to-first-start includes precommit time; it is not exact acceptance-commit latency.
    
  
    What is a particularly useful failure test to read?
    A separate worker JVM is killed after its claim commits. A surviving platform must record EXPIRED, then claim a replacement that completes. Another test completes in the DB, closes the real Rabbit channel before ACK, then verifies redelivery does not create another attempt.
