# Local scaling results — 2026-10-25

**Conclusion:** more execution slots helped the one-second workload. Moving from
one ten-slot worker to two reduced first-start waiting and backlog at the same
15 jobs/s offer. One twenty-slot worker achieved similar completion throughput
with fewer connections. Neither layout can be declared universally better from
these short shared-host runs. Raising the load overloaded the scaled layout too.

## What changed, and what stayed fixed

Every case used fresh disposable PostgreSQL 17.6/RabbitMQ 4.1.8-management with
the same **one CPU/768MiB per dependency** limits. One API/publisher/retry-recovery
JVM stayed separate from the worker JVMs. Thus this is a new role-separated
baseline; do not interpret differences from Phase 7's combined process as a
controlled performance change.

Each scenario warmed up for ten seconds at 5/s and drained before a **sixty-second
fixed-rate offer**. Each began with exactly fifty stored jobs/attempts/outbox rows.
HTTP threads=16, outstanding requests≤32. No TLS, fresh local TCP per submission.
Payloads remain fixed: a 128-character ECHO message or a no-failure 1000ms
simulation. The JAR/default execution semantics did not change.

The host was macOS 14.6 ARM64, eight logical CPUs, 8GiB RAM. Docker Desktop 28.0.1
had eight VM CPUs and 4,109,803,520 bytes RAM. Host JVMs each used 256–512MiB heap
and `ActiveProcessorCount=2` (not an OS quota). The development app/monitoring and
other machine activity shared these resources. Per-role JSON logs/snapshots and
the experimental SQL/HTTP observer remained enabled.

## Simulation comparison

| Worker layout | Offered/s | Accepted | Completed/s during DB window | Client p99 | First-start p95* | Unfinished at end | Observed additional drain |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| **1 × 10 slots** | 15 | 900 | **9.52** | 32.98ms | **31.26s** | **327** | 36.67s |
| **2 × 10 slots** | 15 | 900 | **14.59** | 39.24ms | **1.03s** | **21** | 2.75s |
| **1 × 20 slots** | 15 | 900 | **14.68** | **358.20ms** | 1.12s | 15 | 2.77s |
| **2 × 10, overloaded** | **25** | 1500 | **17.81** | **782.07ms** | **23.65s** | **427** | 27.60s |

*First-start is creation-to-first-claim, including precommit time, **not** exact
commit-to-start. Actual database completion windows were 60.171308, 60.251959,
60.283135 and 60.256712 seconds. They count 573, 879, 885 and 1073 completions,
respectively. Drain completions are not added to those numerators.

Two workers split their 900 jobs **448/452**; under overload they split 1500 jobs
**740/760**. Every selected job finished correctly with one recorded attempt.
No selected clean run had HTTP errors, generator drops or unknown commit outcomes.
Backlog values include executing plus queued work, not just broker-ready messages.

At 15/s, two workers kept up instead of accumulating the roughly 5/s deficit of
ten slots. The observed throughput increase is **not a universal 2× result**:
input was capped at 15/s, and more processes added CPU/memory/pools. The equal-slot
control is important: a single process with twenty slots also kept up. Its worse
client p99 is a recorded result, not proof of a specific CPU/database cause without
profiling/repetition.

At 25/s, all twenty slots were active in samples and backlog kept rising. The
outbox was empty at the end, so publication was not the only waiting stage. Up to
three pending pool requests appeared in samples; attempt-time variability and
client p99 increased. This supports **execution/resource pressure**, not a proven
single-component saturation cause. No flamegraph, storage-latency or CPU-causal
analysis was performed.

## Connection/resource costs

| Layout | JVMs including API | Max configured heap | Max possible DB connections | Max connections sampled | Max pending pool requests sampled |
| --- | ---: | ---: | ---: | ---: | ---: |
| One worker, either slot count | 2 | 1024MiB | 28 | **24** | 0 |
| Two workers, 15/s | 3 | 1536MiB | 42 | **38** | 0 |
| Two workers, 25/s | 3 | 1536MiB | 42 | **38** | **3** |

Each process can use ten primary and four reserved supervision connections. The
publisher-only process did not need all four control connections; actual totals
were below configured maxima. Connection samples exclude the SQL observer's own
session, but can include platform health/metrics activity. Lock-wait samples were
zero; this does **not** prove lock contention never occurred between samples.
More worker processes multiply memory/connection/supervision/snapshot costs.

Initial database sizes in simulation order: 8,260,755 / 8,293,523 / 8,260,755 /
8,400,019 bytes. Differences reflect metadata/storage timing, not a retained-data
reset inside the case. Stored simulation payload/result JSON UTF-8 sizes were
48/82 bytes; requests were 81 bytes. Database size includes indexes/overhead.

## Publication-wait tuning, not a capacity claim

Both ECHO cases used two ten-slot workers and **15 offered jobs/s**. Only the API
publisher's fixed delay changed; production defaults were **not** changed.

| Publisher delay | Accepted | Completions/s | First-start p95* | Unfinished/outbox at end | Client p99 |
| --- | ---: | ---: | ---: | ---: | ---: |
| Default **1000ms** | 900 | 14.81 | **1.415s** | 7 / 7 | 496.42ms |
| Experimental **100ms** | 900 | 14.95 | **0.120s** | 0 / 0 | 88.16ms |

Both workers handled 450 jobs in each case, with one attempt/result per job. The
approximately 10× smaller polling interval was consistent with a large reduction
in low-load publication waiting. It also performs more empty/short polls and
broker calls; no claim of 10× maximum throughput follows. Client p99 variation
also reflects shared-host effects; it is not solely explained by publication,
because acceptance does not wait for a publisher.

ECHO request/payload/result sizes were 168/143/143 bytes. Both cases started with
fifty warm-up jobs; initial DB bytes 8,309,907 / 8,277,139. Database completion
windows: 60.301103 / 60.202793s, containing 893 / 900 completions. Observed drain:
5.598 / 0.408s; state polling and observation overhead mean this is not exact ACK
latency. Sampled DB connections peaked at 38 / 35, with no sampled pool wait.

## Invalid attempts are not hidden

1. The first **25/s simulation attempt** exceeded the SQL observer's fifteen-second
   subprocess deadline, while application logs also showed dependency/pool/confirm
   errors. The cohort did not produce a valid completed-window report and is
   **excluded**, not claimed recovered or loss-free. Logs were kept, resources
   removed, and the valid rerun is the row above. The exact cause of that transient
   failure is not established. Failure-capture support was added for later attempts.
2. **ECHO at 150/s**, sixteen HTTP threads/32 outstanding: 73 of 9000 planned
   arrivals were dropped by the generator; 8927 accepted jobs finished correctly.
3. A repeated **150/s ECHO** attempt with 32 threads/64 outstanding still dropped
   964 arrivals (909 capacity/55 dispatch-deadline); 8036 accepted jobs completed.
   Larger generator queues were not a fix for shared-machine pressure.
4. **ECHO at 60/s** dropped 123 arrivals (109 capacity/14 deadline); 3477 accepted
   jobs completed. It too is **invalid** as a clean fixed-rate comparison.

These aborted cases are retained with explicit invalid status. They are not
evidence that a clean 150/s or 60/s scaling workload was sustained, nor a precise
application capacity ceiling: the same-host bounded generator and observations
can limit the experiment. Lowering ECHO to 15/s deliberately changed the question
to low-load publication waiting. Do not omit dropped arrivals and present only
successful-request p99.

The digest-pinned Java 21 runtime image built successfully. A unique disposable
Compose project launched one API and two worker containers, each non-root
10001:10001, read-only filesystem, one CPU and 512MiB limit. Twenty one-second
jobs produced **20 attempts, 20 correct results and 2 worker identities**.

Runtime: Temurin 21.0.12.1+1. Image ID:
`sha256:e677c7b68ba4ae711d86b6adf399ea9f788d370233a31f89d8e568bfc12140e7`.
The smoke project's random API port was 55302. It and only its volumes were removed
after verification; the standalone persistent deployment was not left running.
The final repeated smoke strengthened result checks to exact null-safe JSONB
equality and again passed twenty jobs/attempts/results with two workers. That
separate disposable project used port 55303 and rebuilt image ID
`sha256:1b3daed5b3a92db3f96b9e9ee1d3c45d92eb1d506841358477636de00ef87e03`;
its containers/volumes were also removed.
Host-JVM benchmark and CPU-limited container smoke are different resource layouts;
do not compare their throughput as if equivalent.

Full regression: **173 Java tests**; generator/scaling/container checks:
**71 Python tests**; no failures/errors/skips. Development app/monitoring stayed
healthy with original 7 COMPLETED/2 FAILED jobs unchanged. No production execution
code, schema, automatic cleanup or runtime defaults were changed.

## What remains unproven

No Kubernetes cluster/manifests, multi-host HA, autoscaling, full resource-normalized
efficiency study, long soak, maximum-capacity search, exact commit-to-start timing,
1,000/s capacity or 99.9% availability claim. Local scaling completion means the
documented experiments/packaging passed—not that every future exploration in the
design has been implemented.
